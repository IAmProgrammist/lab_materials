### **Функциональные требования (FR)**

1. **Управление проектами и участниками:**
    - Система должна позволять авторизованному пользователю создавать, просматривать и редактировать музыкальные проекты (группы).
    - Для каждого проекта можно задавать название и обложку.
    - Владелец проекта должен иметь возможность приглашать других пользователей в проект, назначая им одну из ролей (`Viewer`, `Editor`, `Owner`) на уровне проекта.
2. **Управление профилями авторов:**
    - Система должна предоставлять возможность создавать и вести профили авторов (исполнителей, композиторов), отдельные от профилей пользователей-менеджеров.
    - Профиль автора должен включать: изображение, ФИО или псевдоним.
    - Автора можно прикреплять к песням.
3. **Версионное управление песнями (треками):**
    - Система должна позволять создавать и редактировать песни с поддержкой версионности для критических атрибутов: статус, название, текст, описание, BPM, прикрепленные авторы/проекты, аудиофайлы, изображения, другие файлы, публичность.
    - Для каждой песни должна вестись история изменений версионных полей с возможностью просмотра и (опционально) отката к предыдущей версии.
    - К песне можно добавлять неверсионные комментарии.        
4. **Управление правами доступа к объектам:**
    - Система должна реализовывать двухуровневую ролевую модель:
        - **Глобальный уровень портала:** роли `User`, `Manager`, `Composer`, `Admin` определяют общий доступ к функциям системы.
        - **Уровень объекта (проект, песня, плейлист):** роли `Viewer` (только чтение), `Editor` (чтение и запись), `Owner` (полные права, включая управление доступом) для гибкого распределения прав внутри проектов.
5. **Создание и управление плейлистами:**
    - Пользователи должны иметь возможность создавать плейлисты, добавляя в них конкретные версии песен или привязываясь к их последней актуальной версии.
    - Плейлист должен иметь настройки публичности: приватный (доступ по явному разрешению) или публичный.
    - В публичный плейлист можно добавлять только песни с версионным атрибутом «публичность» = `true`.
6. **Продвинутый аудиоплеер:**
    - Плеер должен обеспечивать базовые функции: воспроизведение/пауза, переход по трекам в плейлисте.
    - Должна присутствовать функция **параллельного воспроизведения** нескольких треков с индивидуальными контролами паузы/продолжения (`продолжить с...`) и общим контроллером «стоп».
    - Плеер должен быть оснащен встроенным **параметрическим эквалайзером** (графическим или набором ползунков) для оперативной обработки звука как отдельного трека, так и микса одновременно играющих треков.
7. **Интеграционный интерфейс:**
    - Система должна предоставлять защищенный API (REST или GraphQL) для потенциальной будущей интеграции со сторонними сервисами публикации треков (например, дистрибуция на Spotify, Apple Music).
    - API должен позволять получать информацию о песнях и их финальных (актуальных) версиях, включая метаданные и файлы.
### **Нефункциональные требования (NFR)**
1. **Производительность и отзывчивость:**
    - Время загрузки основных страниц приложения (Домашняя, Страница проекта) при стабильном интернет-соединении не должно превышать **2 секунд**.
    - Операции с аудио (загрузка трека, начало воспроизведения в плеере) должны выполняться с задержкой не более **1 секунды** при стандартном качестве потока.
    - Интерфейс должен оставаться отзывчивым (без "зависаний") при параллельном воспроизведении до 4 аудиодорожек с активным эквалайзером.
2. **Надежность и доступность:**
    - Уровень доступности (uptime) системы для авторизованных пользователей должен составлять не менее **99.5%** в рабочее время (по часовому поясу основной аудитории).
    - Система должна автоматически сохранять черновые версии песни (автосохранение) не реже, чем раз в **2 минуты**, для предотвращения потери данных.
    - Все загружаемые пользователями файлы (аудио, изображения) должны быть защищены от потери резервным копированием.
3. **Безопасность и конфиденциальность:**
    - Аутентификация пользователей должна осуществляться через внешний надежный провайдер (Keycloak) с поддержкой OAuth 2.0 / OpenID Connect.
    - Ролевая модель и проверка прав доступа должны выполняться на серверной стороне при каждом запросе к защищенным данным (песни, проекты).
    - Приватные плейлисты и непубличные версии песен должны быть абсолютно недоступны для пользователей, не имеющих явных разрешений (`Viewer` и выше).
    - Все данные должны передаваться по защищенному протоколу (HTTPS).
4. **Масштабируемость и архитектура:**
    - Архитектура системы должна быть **клиент-серверной (CSR/SPA)** с отдельным backend API и frontend приложением. Это обусловлено необходимостью создания сложного, интерактивного UI (плеер, эквалайзер, drag-and-drop) без постоянных перезагрузок страниц.
    - Backend должен быть спроектирован как набор микросервисов/модулей (например, отдельно сервис управления проектами, отдельно сервис аудио-обработки/потоковой передачи) для обеспечения независимого масштабирования.
    - Система должна быть способна обслуживать увеличение количества пользователей и проектов на **50%** в течение года без значительной деградации производительности, путем добавления вычислительных ресурсов.
