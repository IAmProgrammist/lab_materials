# **Техническое задание на создание автоматизированной системы "Контроль музыкальных проектов" (BackTrack)**
# 1. Введение
Настоящий документ представляет собой Техническое задание (ТЗ) на разработку автоматизированной системы "BackTrack", предназначенной для комплексного сопровождения и управления процессом создания музыкальных произведений. Система предоставляет инструменты для организации работы музыкальных продюсеров, ведения проектов, контроля версий треков и коллективного взаимодействия.
# 2. Основание для разработки
Основанием для разработки является потребность в унифицированном программном решении, которое устранит разрозненность данных и процессов в работе музыкальных продюсеров, обеспечит централизованное хранение версионных материалов, контроль прав доступа и упростит взаимодействие между участниками творческого процесса.
# 3. Назначение и цели создания системы
**Назначение системы:** Автоматизация процессов управления музыкальными проектами, включая ведение треков, метаданных, авторских профилей, создание плейлистов и обеспечение контроля доступа.
**Цели создания системы:**
- Повышение эффективности работы музыкальных продюсеров за счет структурирования информации.
- Обеспечение сохранности и контроля версий аудиоматериалов и сопутствующих данных.
- Организация безопасного коллективного доступа к проектам и трекам.
- Создание инструмента для оперативного прослушивания и предварительного мастеринга треков.
- Подготовка платформы для последующей интеграции со стриминговыми сервисами.
# 4. Требования к системе
## 4.1. Функциональные требования
### 4.1.1. Подсистема управления проектами и группами:
- Система должна обеспечивать возможность создания, редактирования и удаления проектов (групп).
- Для каждого проекта должна храниться следующая информация: название, обложка.
- Должна быть реализована функция приглашения пользователей в проект с назначением роли для совместного редактирования.
### 4.1.2. Подсистема управления профилями авторов:
- Система должна позволять создавать и вести профили авторов (исполнителей, композиторов), которые не являются пользователями системы.
- Профиль автора должен включать: ФИО/псевдоним, фотографии/изображения.
### 4.1.3. Подсистема управления песнями (треками):
- Система должна предоставлять возможность создания и ведения карточек песен.
- Для каждой песни должна вестись версионная история по следующим атрибутам:
    - Статус (черновик, в разработке, актуально, архив).
    - Название.
    - Текст.
    - Описание.
    - BPM (темп).
    - Список прикрепленных авторов или проектов.
    - Аудиозаписи.
    - Изображения.
    - Прочие файлы.
    - Флаг публичности.
- Должна быть реализована система комментариев к песне (не версионная).
- Должна быть реализована модель разграничения прав доступа на уровне песни.
### 4.1.4. Подсистема управления плейлистами:
- Система должна позволять пользователям создавать плейлисты.
- Плейлист должен иметь настройки видимости: публичный и непубличный.
- Публичный плейлист может включать только треки с версиями, отмеченными как публичные.
- Должна быть возможность привязки к конкретной версии трека или к его последней актуальной версии.
### 4.1.5. Подсистема продвинутого медиаплеера:
- Плеер должен обеспечивать базовые функции: воспроизведение, пауза, переход к следующему треку.
- Должен быть реализован графический эквалайзер для обработки звука как отдельного трека, так и общего микса.
- Должна быть обеспечена возможность одновременного воспроизведения нескольких треков с индивидуальным управлением для каждого (функция "продолжить с...").
- Плеер должен иметь отдельные контролы "Пауза" и "Стоп".
### 4.1.6. Подсистема аутентификации и авторизации:
- Аутентификация пользователей должна осуществляться через внешний сервис Keycloak.
- Должна быть реализована двухуровневая ролевая модель:
    - **Уровень портала:** Роли "Пользователь", "Менеджер", "Композитор", "Администратор".
    - **Уровень объекта (проект, песня, плейлист):** Роли "Пользователь", "Наблюдатель", "Редактор", "Владелец".
### 4.1.7. Пользовательский интерфейс:
- Система должна включать следующие основные экраны:
    - Домашняя страница с виджетами групп, авторов и плейлистов, отсортированными по приоритету доступности для редактирования и пользовательским отметкам.
    - Страница проекта/группы, отображающая список связанных песен и плейлистов.
    - Детальная страница песни.
    - Страница плейлиста.
    - Страница автора.
## 4.2. Требования к надежности
- Система должна обеспечивать целостность и сохранность данных, в особенности версионной истории треков.
- В случае сбоя должно быть обеспечено восстановление (сервиса) в течение не более 1 часа.
- Среднее время наработки на отказ (MTBF) должно составлять не менее 720 часов.
## 4.3. Требования к производительности
- Время отклика системы (Time to First Byte) для любой стандартной операции (открытие страницы, поиск, применение фильтра) не должно превышать 2 секунд.
- Система должна быть рассчитана на одновременную работу до 500 активных пользователей.
- Загрузка аудиофайлов типичного размера (до 500 МБ) не должна блокировать интерфейс для других операций.
## 4.4. Требования к безопасности
- Доступ к системе должен быть разрешен только прошедшим аутентификацию через Keycloak.
- Разграничение прав доступа должно строго соблюдаться в соответствии с двухуровневой ролевой моделью.
- Все данные, передаваемые между клиентом и сервером, должны быть защищены с использованием протокола HTTPS.
- Должна быть обеспечена защита от основных веб-уязвимостей (XSS, SQL-инъекции).
## 4.5. Условия эксплуатации
### 4.5.1. Квалификация персонала:
Пользователи системы должны обладать базовыми навыками работы с веб-приложениями.
### 4.5.2. Технические условия:
- **Клиентская часть:** Система представляет собой веб-приложение, доступное через современные браузеры (Google Chrome, Mozilla Firefox, Safari последних версий). Рекомендуется архитектура **CSR (Client-Side Rendering)** для обеспечения высокой интерактивности и богатого пользовательского опыта, так как система является сложным веб-приложением с динамическим контентом и не предъявляет жестких требований к SEO-оптимизации.
- **Серверная часть:** Должна быть развернута на выделенном сервере или в облачной инфраструктуре (VPS/Cloud) с операционной системой семейства Linux/Windows Server с возможностью увеличения количества реплик
